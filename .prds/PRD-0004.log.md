# PRD-0004 log

Long-form notes that outgrew a task's `notes` field.

## T-007 -- 2026-10-19

The helper's order, and why it differs from a plain reading of the plan in places:

1. Re-parse the targets and `check` them against its own `snapshot()`; refuse patterns outside pid
   1's network namespace. Nothing has changed yet.
2. `create_tun` before sweeping `proto 222`. Holding the device proves no other session is live, so
   a second `sshunnel route` fails on `EBUSY` ("another sshunnel route is running") instead of
   flushing the first one's pins. Teardown deletes pins before dropping the device for the same
   reason.
3. The sweep, then `route_get` for each pin inside a route (pins outside every route are ignored).
4. The closed `plan`: device addresses (the ULA only when a v6 route exists, since adding it where
   IPv6 is disabled fails every run), MTU and link up, pins before the device routes (so ssh's peer
   never routes into a device nobody reads yet), the routes, then resolved: `default-route`,
   `dnssec`, `dnsovertls` and the `~` domains before `dns`, since a link with a server and no
   routing domain is briefly a default route.
5. Any failure after the device exists deletes the pins added so far, replies `Failed`, and drops
   the fd, which takes the device, its routes and its resolved config along.

Every command runs with a cleared environment and a fixed `PATH`: without `secure_path`, sudo keeps
the caller's `PATH`, and the helper must not run an `ip` the caller chose.

`SUDO_UID` unset means the helper serves only its own uid (root). The client strips `SUDO_UID` from
the helper's environment, so a client already running as root (`sudo sshunnel route`) starts the
helper directly and is served; through sudo, sudo sets its own.

`snapshot()` counts on-link unicast routes (no gateway, `via` or `nexthops`; v6 routes carry no
scope) in the tables the rules name, and skips `default`, sshunnel's own device and `proto 222`
pins, so a running session or a dead one's pins never read as connected subnets.

For T-009: `serve` returns its error after replying `Failed`, so the helper's stderr repeats what
the client reports. For T-010: patterns are refused outside pid 1's network namespace (resolvectl
would configure whatever link has the same index there), so namespace tests can't use pattern
targets as the helper stands.

### Review follow-ups

- The helper opens the socket path `O_PATH | O_NOFOLLOW`, requires a socket owned by the served
  uid, and connects through `/proc/self/fd/N`, so a root connect never lands on another file and
  every refusal reads the same (no errno for the caller to probe with).
- `IFF_TUN_EXCL`: an existing `sshunnel0` (a leftover, or one a client made persistent with
  `TUNSETPERSIST`, which needs no capability) is EBUSY, never attached to and configured.
  Teardown clears the persist flag on the helper's fd before closing it. A client that keeps its
  fd past the helper's exit can still set the flag again; nothing the helper does after exiting
  can stop that, and the next start refuses the device rather than reusing it.
- A pin whose current route isn't unicast (a 127.0.0.1 resolver, the host's own address) needs no
  pin, since the local table outranks main, and is skipped. A route that is exactly a pinned host
  is left out, with a warning: the pin wins.
- Commands run in their own process group, so a second Ctrl-C during teardown can't kill
  `ip route del`, and the wait for the setup watches SIGINT, SIGTERM and SIGHUP like every other
  wait.
- `/usr/local` is off the fixed `PATH`; the socket dir's name is random (from `/dev/urandom`), so
  another user can't pre-create it in a shared `/tmp`.

## T-009 -- 2026-10-19

`route::lifecycle::run`, in order:

1. Handle SIGINT, SIGTERM and SIGHUP (`helper::Signals`, now shared). This comes first, so a signal
   during startup ends in an orderly exit. Under the default disposition, a Ctrl-C at the sudo
   prompt would kill the client and leave the helper's socket dir behind.
2. `Targets::parse`, `system::snapshot`, `check` (refusals fail, warnings print), then
   `resolved_usable()` when there are patterns. Then `FakeMap::load` and `upstream_dns()`, read
   once and shared by the pins and the DNS forwarder (`peers::pins` now takes them, and an
   `Option` pid). Nothing here runs ssh.
3. `Session::connect`, the relay line (`Session::describe`, shared with `forward`), then
   `peers::pins`. Both race a signal, which drops the session (ssh is `kill_on_drop`) and exits
   cleanly.
4. `Helper::start`, not raced. sudo handles its own Ctrl-C, and the helper, which sees it too,
   tears down right after `Ready`. A signal pending meanwhile wins the final select at once, since
   that select is `biased` toward signals.
5. `route::device::spawn` (the TUN fd registered with tokio, one reader task and one writer task)
   and `stack::run` with `dns::Server`, all in one `JoinSet`.
6. `ip route get` (in `spawn_blocking`) for each route's first address and, with patterns,
   `198.18.1.1`. A dev other than `sshunnel0` warns, naming it. A pin or a connected subnet's
   address is not probed, since it keeps its route by design. Then the status line.
7. `select!`: a signal is a clean exit; the session ending, the helper's socket closing, or any
   device or netstack task ending is an error.

Teardown runs on every path once the helper has started: `JoinSet::shutdown` (closing the client's
fd), then save the map, then `helper.stop()`, which waits for the helper to delete its pins. The
first error is the exit's; any later one is logged. `Ready` followed straight away by the helper
closing (a Ctrl-C during setup) is the select's helper branch or its signal branch, never a hang.

The helper is quiet about an error it delivered as `Failed`: `serve` returns it marked
`helper::Reported`, and the binary exits 1 without printing it. A `Failed` that couldn't be sent
(the client gone) is printed as before.

tokio 1.53 deprecates `AsyncFd::new` as unsound and offers only `unsafe fn register`. Its contract
(the fd stays open and the same until the `AsyncFd` drops) holds trivially for an `OwnedFd`, so
`route::device` has the one new `unsafe` block.

Device read and write errors both end the run with context. Warnings print once by exact text, but
the helper re-checks the normalized targets: a warning about a target written without its prefix or
with host bits (`10.99.0.5`, `10.99.1.0/16`) can print a second time, in the normalized spelling.

### Review follow-ups

- The resolved refusal now joins the connected-subnet refusals in one error. `Targets::findings`
  returns them unformatted, `check` wraps it, and `lifecycle::checked` adds the resolver's refusal
  first. Parse errors stay separate.
- Under `nohup`, SIGHUP stays ignored. Registering a handler would override the inherited
  `SIG_IGN`, so the client reads the kernel's `SigIgn` mask from `/proc/self/status` (reading it
  through `sigaction` would take `unsafe`) and handles SIGHUP only when it wasn't ignored. The
  helper still handles all three signals.
- A short write to the device ends the run; a TUN device takes a packet whole or not at all.
- `SshCommand::check_command` is Linux only, with `peers`, so a macOS build has no dead code.
- Reading SIGHUP's disposition fails safe: if `/proc/self/status` can't be read or parsed, the
  client handles SIGHUP as before (logged at debug) rather than refusing to start.

## T-010 -- 2026-10-19

**The harness** (`src/tests/netns.rs`). `netns(name)` first checks that the test binary lists
exactly one test by that name, since a misspelled name would run nothing and pass. It then runs
`<exe> --exact <name> --nocapture` under `unshare -rn` with `SSHUNNEL_IN_NETNS=1`, where the body
runs. Where `unshare -rn true` fails, `/etc/os-release` has `UBUNTU_CODENAME` and `docker info`
works, it runs the same command in
`docker run --rm --init --privileged --network none` as root, with the workspace and target dirs
mounted read-only at their own paths and `timeout 110` (under nextest's 120 s kill) in front. The
image `sshunnel-netns:<codename>` is `ubuntu:<codename>` plus iproute2, built from a Dockerfile on
stdin when `docker image inspect` misses. `SSHUNNEL_NETNS=docker` forces the container. With
neither, the test skips, and fails under `CI`.

**The topology** (`RemoteNs`). The remote's namespace is held by `unshare -n sleep infinity`. The
veth pair is `cl0` 172.31.0.1/30 (the test's side) and `rm0` 172.31.0.2/30, and a dummy link on the
remote holds 10.99.0.5, fd99::5 and 10.98.0.2. On the test's side, `10.98.0.0/16` goes via
172.31.0.2 at metric 100, as a DHCP route would. A `/32` there, as first planned, would outrank any
target by prefix length, so the pin would go untested, and the pin's own `ip route add` would then
fail with EEXIST. With the metric-100 route, a `10.98.0.0/16` target captures the peer and only the
pin keeps it. Nothing on the test's side reaches 10.99.0.0/16 or fd99::/64 except a route's
device, so the byte-exact echo can only have crossed the tunnel. ssh's own connection is a bash
`ssh` holding `/dev/tcp/10.98.0.2/2222` in the test's namespace, with the fake remote as its child
(an exec would carry the socket into the remote's namespace, where `/proc/<pid>/net/tcp` can't see
it). A variant closes ssh's own copy and leaves the connection to a child, as `ProxyCommand nc`
does; scanning ssh's pid alone, rather than its process tree, fails that test. `FakeRemote` gained `in_netns`, `with_hosts` (`unshare -m` plus bind-mounted `/etc/hosts` and
an `nsswitch.conf` of `hosts: files`, so the relay on this same machine never asks the resolver
that `route` points back at it) and `with_master` (the `ssh -O check` answer).

**Exit paths**, each a namespace test (`e2e_route_teardown_*` unless named):

| Path | Test | Result |
|---|---|---|
| SIGTERM to the client | `after_a_clean_exit` | exit 0; device, routes, pin gone |
| Ctrl-C to the whole process group | `when_ctrl_c_reaches_every_process` | exit 0; all gone |
| A signal during session connect | `after_a_signal_during_connect` | exit 0; nothing was made |
| SIGKILL to the client | `after_sigkill` | the helper deletes the pin; all gone |
| SIGKILL to client and helper | `after_sigkill` | pin left; the next start sweeps it |
| The session drops | `after_the_session_drops` | non-zero, "the ssh session ended"; all gone |
| SIGINT to the helper alone | `when_the_helper_gets_sigint` | non-zero, "the root helper exited"; all gone |
| SIGKILL to the helper | `when_the_helper_dies` | non-zero; device and routes gone |
| The device deleted (`ip link del`) | `when_the_device_is_deleted` | non-zero, the read error; all gone |
| `Helper::start` fails | `e2e_route_one_session_at_a_time`, `e2e_route_patterns_need_the_init_netns` | the helper's error; nothing changed |

A declined or missing sudo can't happen as root; the helper's unit tests cover it
(`a_declined_sudo_is_a_clean_error`, `a_missing_sudo_is_a_clean_error`).

**What the suite found:**

- A deleted device hung the run. A TUN device whose interface is gone polls as `EPOLLERR` alone,
  which tokio maps to error readiness, never readable, so the reader waited forever and nothing
  noticed. The reader now waits for `READABLE | ERROR`
  (`a_device_that_fails_ends_the_reader_with_an_error`).
- The Task 7 minor: clearing the persist flag on a deleted device fails with EBADFD, so the helper
  exited 1 after a complete teardown. EBADFD now means nothing is left to clear
  (`a_deleted_device_has_no_persist_flag_to_clear`).

**Not changed, for a decision:**

- Adjacent targets aggregate (`10.98.0.0/16` and `10.99.0.0/16` become one `10.98.0.0/15` route,
  by design). An existing route equal to one of the user's targets, even at a worse metric, then
  outranks the aggregate by prefix length; the route check warns, naming its device.
- A pin whose address already has a host route in main (OpenVPN adds one for its server) fails
  setup with EEXIST, although the device could never capture it.
- `getent ahostsv6` maps A records into IPv6 (`AI_V4MAPPED`), so with AAAA as NODATA it returns
  `::ffff:198.18.x.y`, not nothing. The root test asserts that no native IPv6 address appears.

**CI.** The `ci` and `codecov` jobs lift `kernel.apparmor_restrict_unprivileged_userns` before the
tests. The `ci` job then runs the namespace suite once more with `SSHUNNEL_NETNS=docker`
(`route-docker`), and the two `tests/route_root.rs` tests as root
(`route-root`, `sudo -E` as the target runner).
