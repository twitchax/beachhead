# PRD-0004 log

Long-form notes that outgrew a task's `notes` field.

## T-007 -- 2026-10-19

The helper's order, and why it differs from a plain reading of the plan in places:

1. Re-parse the targets and `check` them against its own `snapshot()`; refuse patterns outside pid
   1's network namespace. Nothing has changed yet.
2. `create_tun` before sweeping `proto 222`. Holding the device proves no other session is live, so
   a second `sshunnel route` fails on `EBUSY` ("another sshunnel route is running") instead of
   flushing the first one's pins. Teardown deletes pins before dropping the device for the same
   reason.
3. The sweep, then `route_get` for each pin inside a route (pins outside every route are ignored).
4. The closed `plan`: device addresses (the ULA only when a v6 route exists, since adding it where
   IPv6 is disabled fails every run), MTU and link up, pins before the device routes (so ssh's peer
   never routes into a device nobody reads yet), the routes, then resolved: `default-route`,
   `dnssec`, `dnsovertls` and the `~` domains before `dns`, since a link with a server and no
   routing domain is briefly a default route.
5. Any failure after the device exists deletes the pins added so far, replies `Failed`, and drops
   the fd, which takes the device, its routes and its resolved config along.

Every command runs with a cleared environment and a fixed `PATH`: without `secure_path`, sudo keeps
the caller's `PATH`, and the helper must not run an `ip` the caller chose.

`SUDO_UID` unset means the helper serves only its own uid (root). The client strips `SUDO_UID` from
the helper's environment, so a client already running as root (`sudo sshunnel route`) starts the
helper directly and is served; through sudo, sudo sets its own.

`snapshot()` counts on-link unicast routes (no gateway, `via` or `nexthops`; v6 routes carry no
scope) in the tables the rules name, and skips `default`, sshunnel's own device and `proto 222`
pins, so a running session or a dead one's pins never read as connected subnets.

For T-009: `serve` returns its error after replying `Failed`, so the helper's stderr repeats what
the client reports. For T-010: patterns are refused outside pid 1's network namespace (resolvectl
would configure whatever link has the same index there), so namespace tests can't use pattern
targets as the helper stands.

### Review follow-ups

- The helper opens the socket path `O_PATH | O_NOFOLLOW`, requires a socket owned by the served
  uid, and connects through `/proc/self/fd/N`, so a root connect never lands on another file and
  every refusal reads the same (no errno for the caller to probe with).
- `IFF_TUN_EXCL`: an existing `sshunnel0` (a leftover, or one a client made persistent with
  `TUNSETPERSIST`, which needs no capability) is EBUSY, never attached to and configured.
  Teardown clears the persist flag on the helper's fd before closing it. A client that keeps its
  fd past the helper's exit can still set the flag again; nothing the helper does after exiting
  can stop that, and the next start refuses the device rather than reusing it.
- A pin whose current route isn't unicast (a 127.0.0.1 resolver, the host's own address) needs no
  pin, since the local table outranks main, and is skipped. A route that is exactly a pinned host
  is left out, with a warning: the pin wins.
- Commands run in their own process group, so a second Ctrl-C during teardown can't kill
  `ip route del`, and the wait for the setup watches SIGINT, SIGTERM and SIGHUP like every other
  wait.
- `/usr/local` is off the fixed `PATH`; the socket dir's name is random (from `/dev/urandom`), so
  another user can't pre-create it in a shared `/tmp`.
