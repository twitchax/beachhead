# PRD-0008 log

## Rulings -- 2026-10-27

Decisions made while the plan ran, beyond what the PRD or the plan said. Each one gives the reason,
and what it costs if it's wrong.

- **The sudo probe runs `sudo -n -k`, not `sudo -n`** (T-002's review). A cached sudo timestamp
  made `sudo -n` succeed under a password rule. `--check` (and `sudoers`' last line) then said "no
  password" until the timestamp expired, which is exactly the wrong answer for a script. With a
  command, `-k` ignores the cached credentials for that call without invalidating them. Checked
  against sudo and sudo-rs 0.2.13. Cost: a user with a fresh timestamp sees "asks for a password"
  while `route` would in fact start unprompted right then. `route` itself still runs plain
  `sudo --`.
- **`route --check` and `sudoers` also ask sudo about `/usr/local/bin/sshunnel`** (the final
  review). After the printed setup, a `cargo install` user runs `sshunnel` by name, which is
  `~/.cargo/bin/sshunnel`. Its probe still prompted, so `--check` pointed back at
  `sshunnel sudoers`, which printed the same setup again. The second probe runs only in that case:
  the running copy prompts and isn't root-only, and the installed copy exists, is root-only, and
  isn't the running one. When sudo allows the installed copy, both commands say to run `route` as
  that copy. Cost: a second brief root helper, and one more auth-log line, in that case only.
- **`sudoers` refuses user names that sudoers reads as more than this user**: `ALL`, a leading `+`
  (a netgroup), and an alias-shaped `^[A-Z][A-Z0-9_]*$`. Without this, a user named `ALL` would get
  a line granting every user. Cost: a user whose login is all caps writes the line by hand. A
  `#uid` line is the better follow-up.
- **A user-writable `/usr/local/bin` gets a way forward.** The refusal shows
  `sudo install -D -o root -g root -m 0755 <exe> /opt/sshunnel/bin/sshunnel` and says to run both
  `sudoers` and `route` as that copy. It shows the command only when the exe path is plain and every
  existing directory on the way to `/opt/sshunnel/bin` is root-only. Otherwise it says which one
  isn't.
- **`script(.., AlreadyRoot)` is an error**, with the subcommand's as-root message. The subcommand
  bails as root before it probes, so this only keeps the public function total.
- **The `sudoers` e2e test branches on the host.** Where `/usr/local/bin` is root-only (CI), it
  checks the printed script. Elsewhere it checks the refusal. Each branch runs somewhere.
- **The writable-parent test runs as root in namespaces** (the `netns(...)` guard), instead of
  skipping unless it is root. It asserts which directory made the path unsafe, so the test can't
  pass on `/tmp`'s sticky bit alone.
- **`check::run` has a `pub(crate)` seam that takes the sudo probe.** The crate is edition 2024,
  where `env::set_var` is unsafe, so the signal test injects a shim probe instead of changing
  `PATH`.
- **The planned help text yields to the code on facts** (T-005). See below.

## T-005 -- 2026-10-27

Nine sentences of the plan's exact help copy were changed to match the code. All nine were checked
again by the task review.

- guide: "Nothing is installed system-wide": the relay is cached on the remote.
- guide: sudo asks "as sudo usually does": `route` runs sudo without `-k`, so a cached timestamp
  applies.
- guide: "the `error:` message on stderr says why": a refusal spans several lines, and a usage
  error ends with clap's hint.
- guide: exit 0 "when a signal stops it once ready": `forward` registers its handlers just before
  the ready line.
- route: "A routed name resolves ...": an exact-name target gets a fake address too.
- route Troubleshooting: "another sshunnel route is running" is what a second `route` gets (EBUSY).
  "creating the TUN device" is the context for every other driver error.
- route: "a kill -9 of the root helper": killing the client leaves nothing behind.
- forward: `0.0.0.0` is "every IPv4 interface".
- forward: the stderr sample gains the `relay ... cached in` line `forward` prints first.

The task review then removed "every problem at once". Target refusals stop `preflight` before the
machine's checks run, so each stage reports its own problems together.

## Deferred from the reviews -- 2026-10-27

What the task reviews and the whole-branch review found and left for later, so it outlives the
plan's ledger. The final review triaged each one as fine to ship in 0.2.2.

- **Signals** (T-001): non-unix `StopSignal::recv` still awaits `ctrl_c()` lazily, and its
  `#[expect(clippy::unnecessary_wraps)]` is checked by no CI target. No test pins the registration
  order, since the race can't be forced. The order is visible in `forward`.
- **The probe** (T-002): any exit before the helper connects counts as `Prompts`, including a
  helper that sudo started and that died early. Exit statuses can't tell those apart.
  `probe_with` repeats `start_with`'s SocketDir, bind and spawn steps; a shared `launch()` would
  stop them drifting apart. A multi-line `fail` detail (preflight's joined refusals) puts
  continuation lines under a check line.
- **`sudoers`** (T-003): `sudoers_root_only_accepts_a_system_binary` fails rather than skips on a
  non-FHS host (NixOS). No Ctrl-C handling surrounds the probe, so an interrupt can leave an empty
  socket dir in `$XDG_RUNTIME_DIR`. The refusal branch of `e2e_sudoers_prints_the_setup` expects
  the install command, so a checkout path with a space fails it.
- **Completions** (T-004): `completable()` re-states the name and version instead of reading
  `Cli::command()`'s, so root args added to `Cli` later would drop out silently. The test's
  `!contains("helper")` would fail, never pass, if a description ever said "helper". It covers bash,
  zsh and fish only.
- **The help** (T-005): the troubleshooting test accepts a match in test code or comments, though
  all eight quotes exist in product code today. On macOS the guide's "More:" line names `route` and
  `sudoers`. `lifecycle.rs`'s refusal and `resolver_wired`'s doc still say "nss-resolve" where the
  check reads the `hosts:` line for `resolve`. The help's "0 otherwise" for `--check` doesn't
  mention a check stopped by a signal.
- **Older**: three rustdoc private-link warnings (in `helper` and `names`) predate this PRD. A
  replaced running binary ("(deleted)") now makes `--check`'s `sudo` line `fail` instead of `warn`.
