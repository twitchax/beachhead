# Summary
Milestone 3 carries UDP and ping where M2 carried only TCP. `sshunnel route` sends UDP and ICMP echo
to routed addresses through the relay, gives matched names fake IPv6 addresses beside their v4 ones,
answers every DNS record type for them from the remote's resolver, answers reverse lookups of fake
addresses, and serves DNS over TCP. `sshunnel forward` gains UDP forwards (`-L 5353:dns:53/udp`),
which `ssh -L` can't do. Protocol v4 adds datagram flows to the mux without giving up its rule that
the frame reader never blocks.

# Problem
M2's `route` refuses everything but TCP: UDP and ICMP to a routed address get ICMP administratively
prohibited, so DNS servers, QUIC, VoIP, WireGuard, syslog and `ping` behind the remote all fail.
Matched names answer A alone, so SRV-driven clients (Kerberos, LDAP, SIP, XMPP) and MX or TXT lookups
find nothing, AAAA gets NODATA, and a reverse lookup of a fake address shows a bare IP. The DNS
server answers UDP only, so a truncated answer's retry over TCP fails. And `forward` has no UDP at
all, the gap `ssh -L` leaves open.

# Goals
1. UDP to routed CIDRs and fake addresses works, over v4 and v6, and fails the way a real network
   fails it (a closed port is ECONNREFUSED).
2. `ping` works through `route`, over v4 and v6, to CIDRs and to fake addresses.
3. UDP forwards in `forward`, root-free and on every client platform.
4. Matched names answer AAAA (fake), every other record type (the remote's), and PTR (local).
5. DNS over TCP on the DNS server.
6. A UDP flood can't stall TCP, and a big TCP transfer can't starve DNS or ping.

# Technical Approach

## Decisions (Aaron's, from the 2026-10-20 grilling)
- **Scope:** UDP through `route`; UDP forwards in `forward`; ICMP echo through `route`; every DNS
  record type for matched names; fake IPv6 addresses; DNS over TCP. Out: other ICMP (traceroute's
  time-exceeded), multicast and broadcast, and a UDP bench.
- **Per-flow UDP on the wire.** Each flow is its own mux stream, and the relay holds a connected
  UDP socket per flow (dialed by name for fake addresses), so the kernel filters replies and a
  remote port-unreachable comes back as `ECONNREFUSED`. Over one shared, address-per-datagram socket.
- **Flow limits, after conntrack:** 30 s idle until a flow has seen more than one reply, 120 s
  after; 4096 flows per session; least recently used evicted at the cap; the relay raises its
  open-file soft limit to the hard limit at startup. All constants, no flags.
- **Datagrams skip credit.** Bounded queues that drop when full; the writer alternates datagrams
  and stream data so neither starves. Credit stays for streams: their bytes can't be dropped once
  accepted.
- **Flows are fair to each other** (Q19, from the builder check): each flow has its own bounded
  queue, and the writer at each end goes round-robin over the flows with datagrams waiting, so a
  flood costs only its own flow. Over one shared datagram queue, where one flood drops everyone's.
- **`forward` syntax:** Docker's suffix, `-L [bind:]port:host:hostport/udp`; `/tcp` is the default
  and may be written. Each local sender is a flow; listeners on both loopbacks, as `-L` today.
- **Ping:** echo only, v4 and v6, through the relay's unprivileged ping sockets. Where the remote
  refuses them, echo gets today's administratively prohibited and `route` warns once at startup.
- **Fake IPv6:** `2001:2::/96` (inside RFC 5180's benchmarking range) with the name's v4 fake in the
  low 32 bits: one table, one state file, the two always paired. AAAA is answered only when the
  machine has IPv6; otherwise NODATA, as today.
- **DNS for matched names:** A and AAAA fake; HTTPS and SVCB NODATA (their `ipv4hint` and
  `ipv6hint` would hand browsers real addresses); every other type forwarded raw to the remote's
  resolver through a new frame, with A and AAAA records removed from anywhere in the answer.
- **PTR** for both fake ranges, answered locally from the fake-address map.
- **The root helper still trusts nothing the client sends:** it decides whether fake v6 is on and
  builds the reverse zones itself; neither travels in the client's `Setup`.
- **No UDP bench.** UDP over one TCP pipe can't promise a rate; the starvation test stands in.
  PRD-0004's T-014 (the route-download stalls) stays parked.
- **Ships as `0.2.0`** (after PRD-0005's `0.1.0`), through a separate `/ship-it` run.

## Protocol v4
`VERSION` becomes 4. The client always pushes its own relay, so both ends always match: no shim for
v3. The builder picks frame layouts; the shapes:
- **Opening a flow:** a UDP open (host, port) on a new stream id, answered by `OpenOk` or `OpenErr`
  with today's kinds; an echo open (host) the same way. Resolution is the relay's limited
  `getaddrinfo` path (below).
- **`Datagram { stream, data }`:** one datagram, at most `MAX_PAYLOAD`. Never counted against credit.
  On an echo flow a datagram is family-neutral, an echo's sequence number and payload, so the
  relay's ping socket can be whichever family the name resolves to on the remote.
- **A flow error:** the relay reports a socket error on a live flow without closing it. It reports
  what a connected socket on Linux reports without `IP_RECVERR`: `ECONNREFUSED` (port
  unreachable), `EHOSTUNREACH` and `ENETUNREACH`. No error-queue draining.
- **Closing a flow:** `Rst` from either side, reused. The client owns flow lifetime (it sees the
  app's traffic); the relay closes the socket when the client ends the flow.
- **`Query` / `Answer` / a query error:** one raw DNS message each way, on its own stream id, with
  the transport the asker used (UDP or TCP). Like `Resolve`, they ride the control path and are
  never dropped; the client gives up on a query after a timeout (`resolve` has none today).
- **`Hello`** gains the relay's capabilities: ping over v4, ping over v6.

**Receiving datagrams.** The reader hands a `Datagram` to its flow's queue with a non-blocking
send; a full queue (or a flow that's gone) drops it and counts it in a debug log. Queues are small
and bounded (the builder sizes them in datagrams and bytes), so memory stays at queue × flows, the
datagram analogue of window × streams.

**Sending datagrams.** The writer today drains a control channel, then a bounded data channel
(`DATA_QUEUE`, 16). Each flow gets a small bounded send queue of its own, and the writer keeps a
ring of the flows with datagrams waiting: it takes one datagram from the next flow in the ring, then
one frame from the data channel, and so on, whenever both kinds are waiting. A flood on one flow
gets at most its turn in the ring, and datagrams as a whole get at most every other frame. A
datagram that finds its flow's queue full is dropped at the sender, not awaited. The same writer
runs at both ends, so the relay's replies are just as fair.

**The `Tunnel` trait** gains a flow (open by host and port, then send and receive datagrams, plus
flow errors), an echo flow, and a raw query. `Mux` implements them; `forward` and `route` use only
the trait, as they do for streams.

## The relay
- **Lookups stay bounded.** Every open (TCP `Open` included) resolves through the `MAX_LOOKUPS`
  semaphore and the `getaddrinfo` path `Resolve` uses, then connects to the addresses it got. Today
  `Open` calls `TcpStream::connect((host, port))`, whose own lookup skips that limit; with thousands
  of flows a slow resolver could fill the blocking pool that the relay's stdin and stdout also run
  on, and stall its reader. This fixes that latent M2 issue too.
- **UDP flows:** a connected `tokio::net::UdpSocket` per flow; datagrams both ways; socket errors
  become flow errors.
- **Ping:** at startup the relay tries a `SOCK_DGRAM` / `IPPROTO_ICMP` socket and its v6 twin and
  reports what worked in `Hello`. An echo flow is a connected ping socket of the family the target
  resolves to (a CIDR target's own family); if that family can't ping, the open fails and the client
  answers administratively prohibited. The relay builds the echo header around the sequence and
  payload it gets; the kernel sets the identifier. `socket2` (pure Rust, already in the tree through
  tokio's `net`) or a `libc::socket` with a `// SAFETY:` comment; nothing with C code.
- **Query:** the relay reads the `nameserver` lines of its own `/etc/resolv.conf` (a resolver on
  the remote's loopback, like resolved's 127.0.0.53, is fine: the relay is local to it) and sends the
  raw message over the transport the client named to each in order, 2 s each. A truncated answer to
  a UDP query goes back as it is, so the asker retries over TCP (T-009) and that retry reaches the
  relay as a TCP query. It returns the first answer, or a query error when none answers. The
  timeouts need tokio's `time` feature, which the relay doesn't have yet.
- **File descriptors:** at startup, `setrlimit(RLIMIT_NOFILE)` raises the soft limit to the hard
  limit. Many systems set the soft limit to 1024; flows and streams share it.

## Flows
One flow-table type serves both modes, keyed by what identifies a flow there (a local sender for
`forward`; source and destination address and port, or the echo identifier, for `route`).
- **Timeouts:** 30 s idle until the flow has carried more than one reply, then 120 s.
- **Cap:** 4096 flows per session, counted across every `forward` listener and `route`'s UDP and
  echo flows. Opening one more evicts the least recently used (its relay socket closes with it).
- **Before the relay answers:** datagrams from the app wait in the flow's bounded queue until
  `OpenOk`, the datagram analogue of M2's held SYN, and go when it arrives. On `OpenErr`, `route`
  answers the queued datagrams with an ICMP unreachable; `forward` drops them.

The table's tests run on tokio's paused time (uat-006), as M2's held-SYN tests do.

## `forward` with UDP
`Forward::from_str` accepts an optional `/udp` or `/tcp` suffix on the spec. A UDP forward binds a
`UdpSocket` on each loopback (or on the given bind address), and each sender address becomes a flow:
the first datagram opens it, replies go back to that sender from the listening socket. Errors from
the remote end a flow quietly (there's no ICMP to synthesize in user space). The listeners share
the session, so the flood tests (uat-005) run here, root-free. One: a TCP forward moves a fixed
transfer while a UDP forward is saturated on the same session, and the transfer must finish within
a bound set from its unloaded time. Two: while one UDP flow is saturated, a second flow's
request-and-reply exchanges (a ping-pong, as DNS does) keep succeeding, within a loss bound the
builder sets from a run without the flood.

## `route` UDP
`classify` (in `route::stack`) sends UDP to a routed address (not the DNS address) to the flow
table instead of `icmp_error(Prohibited)`, through the same raw-packet path the DNS server uses (no
smoltcp UDP sockets; the `socket-udp` feature can go if nothing else uses it). The router decides
the destination as for TCP: a CIDR target dials the address, a fake address dials the name. Replies
are built as IP/UDP packets (`udp_packet` exists) from the flow's addresses. A flow's replies are
taken from its queue only while the engine's outbound queue isn't backlogged (`Engine::send_opt`
appends to an unbounded queue), so a flood drops at the bounded flow queues instead of growing
memory on the netstack thread. A flow error becomes an ICMP destination unreachable (port, host or
net) quoting the flow's last datagram's IP header and first 8 bytes, as RFC 792 and RFC 4443 ask. The device's MTU is 65535, so the kernel doesn't
fragment datagrams on their way in, and v4 fragments still fail to parse, as in M2.

PRD-0004's uat-009 narrows here: UDP passes, and administratively prohibited stays for ICMP other
than echo (and for echo when the remote can't ping, T-006). Its `admin_prohibited` tests change with
T-005, and PRD-0004 gets a History line saying so.

## `route` ping
An ICMP echo request (v4 type 8, v6 type 128) to a routed address opens an echo flow keyed by
source, destination and echo identifier. The client sends the sequence and payload through the
flow and builds each reply as an echo reply in the app's own family, with the app's identifier and
a fresh checksum, whatever family the relay pinged over (a v6 fake whose name has only v4 on the
remote still answers). When the relay can't ping at all, echo gets administratively prohibited
without opening a flow, and `route` warns once when its routes come up:
`sshunnel: the remote doesn't allow unprivileged ping (net.ipv4.ping_group_range); ping through
the tunnel gets administratively prohibited` (wording is the builder's). Everything else ICMP
stays administratively prohibited; ICMP errors arriving from the app are still dropped.

## Fake IPv6
The v6 fake of a name is `2001:2::/96` plus its v4 fake's 32 bits (`198.18.1.2` →
`2001:2::c612:102`), so it needs no table, no state and no collision handling of its own, and a
name's two addresses always pair.

The helper decides whether fake v6 is on; nothing from the client says so. Today it adds the
device's v6 address (`TUN_ADDR6`) only for v6 device routes, because that add fails the run where
IPv6 is disabled. With domain patterns present it now tries that address anyway: when v6 routes need
it, a failure still fails the run; when only fake v6 wants it, a failure just means fake v6 is off.
With the address up, the helper routes `2001:2::/96` to the device, and its `Ready` reply (warnings
only, today) tells the client whether fake v6 is on, so the DNS server answers AAAA with the v6 fake
or keeps NODATA.

`2001:2::/96` is reserved the way `198.18.0.0/15` is (`route::targets`, re-run by the helper as
root): a v6 target inside it is refused, and one containing it is carved around it with a warning.
That applies whether or not fake v6 ends up on, since `Targets::parse` doesn't know the machine; a
target as wide as `2000::/3` costs about 90 extra routes against the 4096 cap. The router maps a v6
fake back to its v4 fake, then to the name.

## DNS records, PTR and TCP
For a matched name (`routes_name`), by query type:
- **A, AAAA:** as now, fake (AAAA per the section above).
- **HTTPS (65), SVCB (64):** NODATA. Their address hints would bypass the fakes, and browsers fall
  back to A and AAAA.
- **Everything else:** forwarded raw through `Query`. In the answer, every A and AAAA record (answer,
  authority and additional sections) is removed before it goes back, so glue in SRV and MX answers
  can't hand out real addresses; the client then asks A for the target name and gets its fake. No
  cache of its own (resolved caches). A name's existence comes from `Resolve`'s verdict (its 60 s
  cache), as for A: when `Resolve` found the name, a remote NXDOMAIN becomes NODATA (a name only in
  the remote's `/etc/hosts` is unknown to its nameservers, and a cache applying RFC 8020 would let
  that NXDOMAIN hide the name's fake A); when it didn't, NXDOMAIN as today. Other rcodes pass
  through.

**PTR:** a query under `18.198.in-addr.arpa`, `19.198.in-addr.arpa` or the nibble zone of
`2001:2::/96` answers the name for an assigned fake (from `FakeMap::name`) and NXDOMAIN otherwise.
When domain patterns are present, the helper adds those zones to the link's routing domains
(`resolvectl domain sshunnel0 ~corp.example ~18.198.in-addr.arpa ~19.198.in-addr.arpa ~<v6 zone>`;
the v6 zone only with fake v6 on). The helper builds these itself, not from the client.

**TCP on 198.18.0.2:53:** `classify` sends TCP to the DNS address and port to a local smoltcp socket
the DNS server owns (RFC 7766 framing: a two-byte length per message, several messages per
connection, an idle close) instead of the router. Matched names answer as over UDP; forwarded names
go upstream over TCP when they arrived over TCP. That makes a truncated answer's retry work, which
M2's README lists as a caveat.

# Assumptions
- PRD-0005 has shipped `0.1.0`, so M3's protocol change starts a new version.
- The remote is Linux (x86_64 or aarch64) and keeps its resolvers in `/etc/resolv.conf`.
- systemd distributions open `net.ipv4.ping_group_range` to every group by default; many containers
  and Alpine don't, which is the warning's case.
- Apps cope with lost datagrams (that's UDP), and with AAAA answers for names whose remote hosts
  have only v4: the relay dials by name, so the client's family doesn't constrain the remote's.

# Constraints
- The relay: no clap, no tracing-subscriber, nothing with C; its dependency list is its size budget.
- Nothing on the netstack's thread may block (from PRD-0004's T-013): flow tables, echo handling and
  the DNS server's TCP socket all run there without blocking calls.
- `forward` stays cross-platform: its UDP must build and pass its tests on macOS (`cargo check
  --target x86_64-apple-darwin` in CI).
- `route` stays Linux-only.
- One flow per relay socket, so the fd soft-limit raise matters; a remote with a low hard limit
  still caps flows, and a failed socket is an `OpenErr`.

# Non-Goals (MVP)
- ICMP other than echo (traceroute, time-exceeded, path-MTU messages from the remote).
- Multicast and broadcast (mDNS, SSDP).
- A UDP throughput bench or bar.
- Reverse (remote-to-local) UDP forwards.
- DNSSEC validation, and caching of forwarded record types.
- Fake addresses for search domains, and route on macOS.
