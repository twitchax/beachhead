# Summary
Cut sshunnel's first release, `0.1.0`, covering M1 (`forward`, the relay, the bootstrap) and M2
(`route`). The GitHub release keeps coming from `release.yml` on a `v*` tag, and the three crates
(`sshunnel-mux`, `sshunnel-relay`, `sshunnel`) go to crates.io from Aaron's machine through
`/ship-it`. The work here makes the crates publishable: the client's crate carries its relays, the
relays stop recording the paths of the machine that built them, the test fixtures leave the public
API, and CI's actions move off Node 20.

# Problem
Nothing has shipped. Both milestones sit under `[Unreleased]` in the CHANGELOG, and M3 is about to
change the wire protocol, so this is the natural point to pin a working version.

The crates aren't publishable as they stand:
- `build.rs` embeds relays only when `SSHUNNEL_EMBED_RELAY_DIR` names a directory of them. A
  `cargo install sshunnel` from crates.io would get a client with no relays, which fails on every
  remote unless the user finds relays and passes `--relay-dir`.
- A locally built relay carries the builder's paths (45 `/home/...` strings in each of today's
  relays: panic locations and dependency source under `~/.cargo` and `~/.rustup`). Publishing one
  puts a username into a public artifact.
- `sshunnel::tests`, the fixture factory (fake remotes, the namespace harness, the Docker runner),
  is a `pub mod` in every build, so it would become public API on docs.rs.
- `release.yml` and `build.yml` use `actions/upload-artifact@v4` and `download-artifact@v4`, which
  run on the deprecated Node 20.

# Goals
1. `cargo install sshunnel` gives a working client with both relays embedded, offline, with no
   extra steps.
2. No relay, wherever it's built, contains its builder's paths.
3. The published library's API is the product's, not the test harness's.
4. A rehearsed ship: every check passes and the release stops one step short of outward-facing
   until Aaron says go.

# Technical Approach

## Decisions (Aaron's, from the 2026-10-20 grilling)
- **Release first, then M3.** This PRD lands before M3 (PRD-0006), which ships as `0.2.0`.
- **Publish all three crates.** `sshunnel` depends on `sshunnel-mux`, so mux must publish;
  `sshunnel-relay` publishes too, so anyone can build the relay from source. `xtask` stays
  `publish = false`.
- **Relays inside the crate** (over a runtime download or a relay-less crates.io client), plus
  `cargo binstall` metadata pointing at the GitHub release's zips.
- **Publishing runs locally** through `/ship-it`, with Aaron logged in to crates.io on this machine.
  No registry token in CI and no trusted-publishing job.
- **The crate's relays are built locally at publish time** (over downloading CI's from the GitHub
  release), with path trimming. They can hash differently from the GitHub release's relays. Every
  client still verifies the relay it embeds, so nothing breaks, and `sshunnel relays` shows exactly
  what a given client pushes. If trimmed builds turn out to be reproducible across machines the
  hashes will match anyway; this PRD doesn't promise it.
- **The fixture factory goes behind a `testing` feature,** off by default.

## Path trimming
`cargo xtask relay` trims paths on the build's command line, never in a manifest: `cargo-features =
["trim-paths"]` in the root `Cargo.toml` (which is also `sshunnel`'s package manifest) would ship in
the published manifest, and stable cargo refuses to parse it. The two ways are `-Z trim-paths` with
`--config 'profile.relay.trim-paths="all"'` (the pinned nightly builds the relays) or
`--remap-path-prefix` in the xtask's `RUSTFLAGS` for the home, cargo, rustup and workspace
directories. A short spike against today's 45 strings picks the one that reaches them all
(`strip = true` already drops symbols, so what's left is mostly panic locations).

Either way the check is the same: after building, `cargo xtask relay` scans each relay for those
four directories (as the build machine has them) and fails naming the first match. The scan is a
pure function over the relay's bytes and a list of paths, unit-tested with a planted path (uat-002's
`builder_paths` tests). The README's relay hashes get regenerated from the trimmed build.

The client binary built by `cargo xtask dist` isn't in scope: it runs on the user's own machine and
isn't pushed anywhere, and a `cargo install` builds it on the user's machine anyway.

## Relays inside the crate
`cargo xtask package`:
1. always rebuilds both relays (the same code path as `cargo xtask relay`, trimmed and checked, with
   a different output directory) into `relays/` at the `sshunnel` crate's root (a new `.gitignore`
   line), with a `SHA256SUMS`, and fails if either arch is missing;
2. runs `cargo package --workspace` (the `include` list names `relays/*` explicitly, which is how a
   gitignored file gets into a package);
3. unpacks the `sshunnel` .crate into a scratch directory and builds it offline **on the stable
   toolchain** (no `rust-toolchain.toml` reaches the scratch directory), with no
   `SSHUNNEL_EMBED_RELAY_DIR` set, against the packaged mux;
4. runs that client's `sshunnel relays` and checks both relays are listed as embedded with the
   packaged hashes (uat-001).

`relays/` stays in place afterwards, because the publish at ship time packages it again.

`build.rs` embeds, in order: `SSHUNNEL_EMBED_RELAY_DIR` when set (today's behavior; `dist` and CI
use it); else the crate's own `relays/`, **only when building from a package**, which `build.rs`
tells by there being no `.git` (directory or file) beside the manifest; else none (the client needs
`--relay-dir`, as a checkout does today). So a `cargo build` in the repository after a `package` run
never embeds that set, which would go stale with the next relay change. Before embedding from either
directory it checks every `sshunnel-relay-*` file against that directory's `SHA256SUMS` and fails
the build on a mismatch or a relay with no line. The sha256 there comes from `sha2` added under
`[build-dependencies]` (it's a regular dependency today), not from shelling out.

The published crates build on stable Rust: nothing in them uses a nightly feature today, the pinned
nightly is the repo's development toolchain only, and step 3 keeps it that way.

`cargo publish --workspace --dry-run --allow-dirty` (uat-003) runs after `cargo xtask package`.
`--allow-dirty` covers only the packaged relays, which are generated and gitignored; at ship time the
tree is otherwise clean and tagged.

## The `testing` feature
`pub mod tests` becomes `#[cfg(feature = "testing")] pub mod tests`. The dependencies only the
factory uses (from the `[dependencies]` and `[dev-dependencies]` tables alike: `tempfile`,
`pretty_assertions`, rustix's pty and termios features, and the like) become optional regular
dependencies that `testing` enables; target-gated ones stay target-gated. Optional dependencies a
default build doesn't enable cost a `cargo install` nothing. The repo's own tests turn the feature
on without anyone passing a flag: a path-only dev-dependency on the crate itself with `features =
["testing"]` does that for `cargo nextest run` and `cargo make ci` alike, and `cargo publish` strips
path-only dev-dependencies from the published manifest. If cargo refuses the self-dependency, the
fallback (approved up front) is `required-features` on the integration tests plus the feature in the
`cargo make` tasks and the README's test commands. uat-004's test fails if the module is reachable without the feature (a
check on the source's cfg gate is enough; a doc-test can't see features).

## Crate metadata
- `keywords` and `categories` on `sshunnel` (empty today), and on mux and relay.
- A short README each for `crates/sshunnel-mux` and `crates/sshunnel-relay`: what the crate is,
  that it's sshunnel's, and a pointer to the main README.
- `include` lists so each package carries its sources, README, LICENSE and (for `sshunnel`)
  `build.rs` and `relays/`, and none of `.prds/`, `.github/`, `xtask/`, `.config/` or `target/`.
  `LICENSE` lives only at the repo root; mux and relay carry that one file (a symlink cargo follows
  when packaging, or whatever packages it without a second copy to keep in sync).
  Whether `tests/` ships is the builder's call; it can't run without the `testing` feature and the
  fixtures' environment anyway.
- `[package.metadata.binstall]` on `sshunnel`: `pkg-url` names `sshunnel_{ target }.zip` under the
  `v{ version }` release, `pkg-fmt = "zip"`. uat-005 checks that template against the targets and
  zip names in `release.yml`, so the two can't drift. Targets the release doesn't build fall back to
  a source build, which binstall does on its own.

## CI on Node 24
Bump `actions/upload-artifact` and `actions/download-artifact` in both workflows to the first
versions that run on Node 24, and check the others the workflows use. Done when a CI run on `main`
shows no Node 20 deprecation annotation. `release.yml` keeps its shape: relays once, a client per
platform with those relays embedded, and a GitHub release with the zips, relays and `SHA256SUMS`.

## Shipping (T-007)
Through `/ship-it`, which reads this repo's own commands first:
1. Doc pass: the CHANGELOG's `[Unreleased]` becomes `[0.1.0]` with its date and an opening
   sentence on the version; README and CLAUDE.md checked.
2. Version stays `0.1.0` (the first release; no bump).
3. Gate: `cargo make ci`, then uat-001 to uat-005.
4. Commit and tag `v0.1.0`. **Confirm**, then push `main` and the tag; `release.yml` builds the
   GitHub release.
5. `cargo xtask package` from the tagged tree, then `cargo publish -p sshunnel-mux`, `-p
   sshunnel-relay`, `-p sshunnel`, each after its dry run and an explicit **confirm**, waiting for
   the index between dependents.
6. uat-006 against crates.io.

# Assumptions
- Aaron is logged in to crates.io on this machine (`cargo login`) at ship time.
- The names `sshunnel`, `sshunnel-mux` and `sshunnel-relay` are still free (they were on
  2026-10-20).
- The pinned nightly's `cargo package --workspace` and `cargo publish --workspace` handle
  unpublished path dependencies between workspace members (stable since cargo 1.90).
- The release's client zips stay named `sshunnel_<target>.zip`.

# Constraints
- The relay stays small, static and free of C; nothing here adds a dependency to it.
- crates.io caps a crate at 10 MB; two relays are about 1.2 MB together.
- No registry credentials in the repo or its workflows.
- A published version can't be unpublished, only yanked: T-007's confirmations are the guard.

# References to Code
- `build.rs`: embeds `sshunnel-relay-*` from `SSHUNNEL_EMBED_RELAY_DIR`; gains the crate-local
  `relays/` and the hash check.
- `xtask/src/main.rs`: `relay` and `dist`; gains `package` and the builder-path scan.
- `Cargo.toml`: `[profile.relay]`, the workspace's package metadata, the `[features]` table, and the
  dev-dependencies.
- `src/lib.rs`: `pub mod tests`, which goes behind `testing`.
- `src/relays.rs`: reads `EMBEDDED`, maps relays to arches, and backs `sshunnel relays`.
- `.github/workflows/release.yml` and `build.yml`: the actions to bump.
- `tests/repo_sync.rs`: where uat-005's binstall check and uat-004's cfg-gate check fit.
- `README.md`: the relay hashes (regenerated) and a new install section.

# Non-Goals (MVP)
- Trusted publishing or any CI publish job.
- Reproducible builds as a guarantee.
- Windows clients, more release targets, Homebrew or distro packages.
- A `cargo-release` config: `/ship-it` tags by hand.
