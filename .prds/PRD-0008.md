# Summary
`sshunnel help` becomes the whole usage guide, written so that a person, or an agent told "read
`sshunnel help` and get me connected through jump.corp.example for `*.corp.example`", can go from
installed to connected without the README. `route` gains what a script or an agent needs to start
it: a dry run (`--check`), a printed one-time sudo setup (`sshunnel sudoers`), and a ready line to
wait for. Shell completions round it out. It ships as 0.2.2 through `/ship-it`.

# Problem
`sshunnel -h`, `--help` and `sshunnel help` print the same thing: one line per command and per
flag. Nothing in the binary says:
- what the targets look like beyond two examples, that patterns need quoting, or how matching works;
- that `route` needs sudo, and systemd-resolved for domain patterns;
- when `route` is up, how to check it, or how to stop it;
- what an error means or what to do about it.

The README covers most of this, but its `--help` blocks are copied by hand, and it isn't there when
someone has only the binary.

An agent hits three walls, even with the README:
- **The sudo prompt.** `route` asks for a password the agent can't type. Setting up `NOPASSWD`
  means copying commands out of the README and filling in the user name and binary path.
- **No dry run.** The only way to find out whether `route` will start is to start it, and then a
  refusal, an ssh failure and the sudo prompt arrive one at a time.
- **No ready signal.** `sshunnel: routing ...` happens to be the last startup line, but nothing
  says so, and `forward` dies by the signal on Ctrl-C (exit status 130) where `route` exits 0.

# Goals
1. `sshunnel help` alone is enough to connect: examples, prerequisites, the readiness and stop
   contract, exit statuses, files and environment, and troubleshooting.
2. A script or an agent can find out, without changing anything, whether `route` will start and
   whether sudo will prompt, and can get the one-time setup that removes the prompt.
3. The README and the binary can't disagree about usage.
4. No public signature changes, and the crates still build on Rust 1.91.

# Technical Approach

**Layout of the help (T-005).** clap already splits the three entry points. `-h` prints the short
help. `--help` and the `help` subcommand print the long help (clap_builder 4.6.7, parser.rs:681),
so no custom `help` subcommand is needed:
- Each command's `about` is one line, and each argument's `help` is one short sentence.
- The detail goes in `after_long_help`, from hand-wrapped ASCII text files in `src/help/`
  (`guide.txt` for the root, then `route.txt`, `forward.txt`, `sudoers.txt` and
  `completions.txt`), included with `include_str!`.
- No `wrap_help`, so the output is the same on every terminal and in every test.
- The root's `after_help`, shown by `-h`, is one line pointing at `sshunnel help`.

The root's long help is the guide:
- examples for `route` and `forward`;
- how it works, in four sentences;
- what `route` needs before it runs, ending at `route --check`;
- running it from a script or an agent: background it, wait for `sshunnel: ready`, read the last
  `error:` line on failure, handle sudo, stop with SIGINT or SIGTERM, the exit statuses, `RUST_LOG`;
- files and environment;
- pointers to each command's help.

`route.txt` covers:
- the target forms, quoting, and matching;
- names and their fake addresses;
- examples, with the lines `route` prints once it's up;
- privileges, the refusals, and troubleshooting: each message a user can see, and what to do about
  it.

**README (T-005).** Every fenced `text` block whose first line is `$ sshunnel` followed by a help
invocation (`--help`, `-h`, or `help ...`) must be the binary's stdout for those arguments. A test
in `tests/cli.rs` checks this. With `UPDATE_README=1` the same test rewrites those blocks in place
instead, so nobody pastes them by hand. The README embeds `sshunnel --help`, `forward --help`,
`route --help`, `sudoers --help` and `completions --help`. Prose the help now states is removed from
the README, and what stays is the narrative: why, how it works, and the DNS, UDP and ping
mechanics. Performance, caveats, install and development stay.

**Ready lines (T-001).** Once its routes are up, `route` prints two more lines after
`sshunnel: routing ...`:
- `sshunnel: check it with \`<command>\``. The command comes from the first target: a pattern
  `*.d` gives `resolvectl query <name>.d`, a name gives `resolvectl query <name>`, and a CIDR gives
  `ip route get <its network address>`.
- `sshunnel: ready (pid <pid>); Ctrl-C or SIGTERM stops it`.

`forward` prints the same ready line after its `forwarding` lines. It also exits 0 on SIGINT or
SIGTERM, as `route` does, instead of dying by the signal: `tokio::signal::ctrl_c`, plus SIGTERM on
Unix.

**`route --check` (T-002).** A flag on `route`, taking the same arguments. Nothing runs as root
except the probe below, and the only side effect is on the remote, where ssh caches the relay as
any run does. It prints one line per check to stdout:

| Check | ok | warn | fail |
|---|---|---|---|
| `targets` | (refusals as today, through `preflight`) | each preflight warning | the refusal error |
| `ssh` | `Session::connect`, then `describe()` | | the connect error |
| `ping` | the relay's capabilities | `PING_WARNING` when it may ping over neither family | |
| `sudo` | root, or a sudo that starts the helper without a password | a sudo that would prompt or refuse | sudo is missing |
| `device` | no `sshunnel0` | | `/sys/class/net/sshunnel0` exists, so another `route` holds it |

Every check runs, whatever the others found. The last line is `sshunnel: route can start`, or the
run fails with `route would not start: N problem(s)`: exit 1, through `main`'s usual `error:` line.

**The sudo probe (T-002).** `helper::probe_sudo`:
1. Opens a helper socket exactly as `Helper::start` does.
2. Runs `sudo -n -k -- <exe> helper --socket <socket>`, with stderr discarded. `-k` ignores a
   cached timestamp for that call, so a password rule can't pass for `NOPASSWD`.
3. Waits, bounded, for either of two things:
   - sudo exits first: sudo wouldn't start the helper without asking, for a password or by
     refusing outright (`Prompts`);
   - the helper connects, and its peer is root (`NoPrompt`). The probe then hangs up, and the
     helper's `read_setup` fails before `apply`, so it exits having changed nothing.
4. Returns `AlreadyRoot` without running sudo when the client is root.

This is exact where reading sudoers isn't. `sudo -n -l` would also succeed for a user with a
password rule plus an unrelated `NOPASSWD` one, and `listpw` settings change what listing needs.
The cost is one root process and one auth-log line per probe. The `NoPrompt` branch can only be
shown with a real passwordless sudo, so `tests/route_sudo.rs` covers it in CI's route-sudo step.
Shim sudos cover `Prompts` and a missing sudo locally.

**`sshunnel sudoers` (T-003).** Linux only, like `route`. It prints a short shell script for a
person to read and run, and runs nothing itself:
1. Install the binary to `/usr/local/bin/sshunnel`, as root, mode 0755. This step is skipped when
   the running binary (`current_exe`, symlinks resolved) is already root-only: owned by root, not
   group- or other-writable, and the same for every directory above it.
2. Write `<user> ALL=(root) NOPASSWD: <path> helper --socket *` to a temporary file, check it with
   `visudo -cf`, and install it as `/etc/sudoers.d/sshunnel`, mode 0440.
3. Run `route` from that copy.

The script's comments say what the line grants: the README's Privileges paragraph moves into
`sudoers --help`.

The last comment line is the probe's answer: sudo asks for a password right now, or it doesn't. The
command refuses (exit 1) rather than print a line that would be unsafe or wouldn't parse:
- a user name or path with characters outside `[A-Za-z0-9._/+-]`;
- run as root, it says to run it as the user who will run `route`;
- when `/usr/local/bin` itself isn't root-only, it says so and shows how to install a root-owned
  copy under `/opt` instead.

The user name comes from `id -un`. When sudo exits before the helper starts, `route`'s error now
ends by pointing at `sshunnel sudoers`.

**Completions (T-004).** `sshunnel completions <bash|elvish|fish|powershell|zsh>` writes
`clap_complete`'s script for `Cli::command()` to stdout. `completions --help` shows where each
shell loads it from. The root command sets `arg_required_else_help`, so bare `sshunnel` prints the
short help and exits 2 instead of a bare usage error.

# Assumptions
- clap renders the long help for `--help` and `help <command>`, and the short help for `-h`. Checked
  in clap_builder 4.6.7.
- Without `wrap_help`, clap doesn't rewrap `about` or `after_help`. In long help it puts each
  argument's help on its own line, indented 10 columns, so argument helps of up to 90 columns fit.
- `sudo -n` exits non-zero without reading a password when it would need one, before it runs the
  command.
- `std::env::current_exe` is `/proc/self/exe` on Linux, with symlinks resolved. That is the path
  `route` already gives sudo.
- clap_complete 4.6.11 needs Rust 1.85. (It does list hidden subcommands, so `completions` builds
  its scripts from a root without `helper`.)

# Constraints
- No public signature changes (0.2.2). New public items, commands and flags only.
- One new dependency, `clap_complete`, optional and behind the `cli` feature.
- `route`, `--check` and `sudoers` stay Linux only. `completions` and the help text build
  everywhere, and the guide marks what is Linux only.
- Examples use documentation names and ranges only: corp.example, lab.example, 10.99.0.0/16,
  192.0.2.0/24, fd99::/64.
- Help text is ASCII, hand-wrapped at 100 columns.

# Non-Goals (MVP)
- A man page (`clap_mangen`): Q1 chose the help text.
- A bare-suffix shorthand, `.corp.example` for `*.corp.example` (Q4). Patterns keep one spelling,
  and the guide says to quote them.
- Machine-readable (JSON) output for `--check`.
- Installing the sudoers line or the completions: sshunnel prints them, and a person runs them.
- Config files, named profiles, a daemon mode or a systemd unit.
- The version bump and the release: `/ship-it` after this PRD closes.
