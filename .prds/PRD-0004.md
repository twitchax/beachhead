# Summary
Milestone 2 adds `sshunnel route`: bring up a TUN device on a Linux client and route chosen CIDRs
and domain patterns through the relay, so remote hosts work by address and by name the way they do
on the remote's own network. TCP only; names work through fake-address DNS, so the remote's
addresses never touch the local routing table.

# Problem
M1 forwards one port at a time, the way `ssh -L` does. The goal from PRD-0002 is that a remote
LAN's hosts and names work from anywhere: `curl http://wiki.corp.example`, `ssh 10.99.0.5`, with no
per-port setup. sshuttle routes subnets this way but can't split by name, and `ssh -D` plus
tun2proxy needs a SOCKS hop and a separate tool. Splitting by domain pattern is the feature neither
has.

# Goals
1. `sshunnel route <destination> <target>...` carries TCP to every CIDR target and every name a
   domain pattern matches, and nothing else.
2. Names resolve on the remote: the relay looks them up, so the remote's own DNS and `/etc/hosts`
   answer, and a name that doesn't exist there fails to resolve here.
3. Connections look as they would on the remote LAN: refused is refused, unreachable is
   unreachable.
4. Leaving no trace: a clean exit, a dropped session and a SIGKILL all restore the machine.
5. Route mode costs no more than 10% of forward mode's single-stream throughput.

# Technical Approach

## Decisions (Aaron's, from the 2026-10-18 grilling)
- **Linux only** in M2. macOS is much later.
- **No full tunnel:** `0.0.0.0/0` and `::/0` are refused; targets are CIDRs (v4 and v6) and domain
  patterns.
- **Domain patterns in M2,** not M3. `*` only as the whole leftmost label: `*.corp.example`
  matches `corp.example` and every name under it at any depth, and `host.corp.example` matches that
  name only. Fully qualified names only: no search domains.
- **Privileges:** a root helper started through `sudo`, never setcap (resolved has ignored
  `CAP_NET_ADMIN` since systemd v256). The README documents a `NOPASSWD` sudoers line for a
  root-owned install.
- **The SYN is held** until the relay's dial succeeds; a refused dial becomes an RST.
- **UDP and ICMP** to routed addresses get ICMP administratively prohibited. They get their own
  milestone, along with raw DNS forwarding (SRV, TXT, MX).
- **A dropped session** exits and tears down; no reconnect.
- **systemd-resolved is required** for domain patterns; without it they fail clearly and CIDR
  targets still work.
- **The relay checks names** (`Resolve`, protocol v3) with the same `getaddrinfo` lookup `Open`
  uses, so what resolves is what connects. AAAA and every other type get NODATA.
- **Fake addresses are hashed from the name and persisted**, so a name keeps its address across
  restarts, collisions included.
- **Excludes** (`-x`) carve CIDRs out of CIDR targets and names out of patterns; an excluded name
  is answered by the normal DNS servers.
- **Refusals:** `/0`; a target equal to or inside a directly connected subnet (a broader one is
  allowed, with a warning that the connected part stays local); a route the main table already has
  at the metric sshunnel's would get (the kernel won't take an equal one, and replacing it would
  leave a trace); and if ssh's peer falls inside a target, it gets a pinned host route.
- **Breadth, for now:** only the literal `/0`s are refused. A deliberate `0.0.0.0/1 128.0.0.0/1`
  works, and the README says the sudoers line lets anything running as the user route any range but
  the default route through a sshunnel device. The `/0` refusal guards against accidents; it is not
  a security boundary.
- **One session at a time,** carrying any number of targets.
- **Tests** run the OS layer in throwaway network namespaces: directly where user namespaces are
  allowed, otherwise in a privileged Docker container. CI lifts AppArmor's restriction per run.
- **Throughput:** the bench gains a route mode with a 90% bar; a miss comes back to Aaron with
  options.

## Command
```
sshunnel route [OPTIONS] <DESTINATION> <TARGET>...
  <TARGET>            10.99.0.0/16, fd00:99::/64, *.corp.example, host.corp.example
  -x, --exclude <T>   carve a CIDR or a name out of the targets (repeatable)
      --ssh-cmd ...   as in `forward`
      --relay-dir ... as in `forward`
```
Matching: the most specific target wins, and an exclude wins a tie. CIDR excludes apply to CIDR
targets and name excludes to patterns; they never cross, so a pattern routes a name by name,
whatever address it has on the remote. Every parse error and refusal is reported at once, before ssh
runs. Besides the refusals above, a bare `*`, a pattern no hostname can match (a non-ASCII label, or
one over 63 bytes: the DNS server's own rule for a name it looks up), and a target equal to or
inside `198.18.0.0/15` are refused (a broader target, such as `128.0.0.0/1`, is allowed with a
warning, and the fake range is carved out of its routes), and so is any pattern when
systemd-resolved isn't usable (the whole run fails, CIDR targets included, rather than
half-working). So are targets that come to more than 4096 routes: each is an `ip` run as root, and
`/128` excludes inside a wide v6 target could carve it into a hundred thousand. The cap is a
parse-time refusal, so the client and the helper apply the same rule, and excludes are carved in
time that grows with the excludes and the routes kept, never their product. Each target keeps a
route of its own (nested and adjacent ones are never merged), so each competes with the machine's
routes on its own prefix; a route equal to one already in the main table at the same metric is
refused, naming the existing route and its device. Device routes go in at metric 0 for IPv4 and an
explicit 1 for IPv6 (where 0 means the kernel's 1024), so both families win a tie with an equal
route at the kernel's default, from RA, NetworkManager or a VPN.

resolved counts as usable when it answers on D-Bus and the system actually asks it: `/etc/resolv.conf`
points at its stub (`127.0.0.53`) or `nss-resolve` is on the `hosts:` line of `/etc/nsswitch.conf`.
Otherwise the link config would apply and patterns would silently do nothing.

## Lifecycle

```text
1. parse targets, snapshot routes and rules, check resolved,
   apply refusals                                                   (no privileges, no ssh yet)
2. start the session (M1: bootstrap, Hello)                          (ssh connects normally)
3. find what the machine depends on (T-008): ssh's peers and its
   upstream DNS servers; any inside a target gets pinned
4. sudo sshunnel helper: create sshunnel0, addresses, routes,
   pinned routes, resolved link config; send the TUN fd back
5. smoltcp on the fd; DNS server on 198.18.0.2; check each target's
   effective route; print one status line
6. Ctrl-C, SIGTERM, the session ending or the helper dying: close the
   fd, the helper removes pinned routes, then deletes the device (its
   config goes with it) and exits, and the client waits for it
```

The session comes up before anything changes, so ssh's own connection is established on the
machine's normal routes, and its peer is known before step 4 could capture it.

**Pinning what the machine depends on.** Two kinds of address keep their pre-TUN route when a target
contains them (one with a host route of its own in the main table keeps it anyway, so it gets no
pin):
- **ssh's peers:** the remote addresses of TCP sockets held by ssh's process tree, which covers a
  `ProxyCommand` child. With connection sharing (`ControlMaster`), the spawned ssh holds no socket
  and a `ControlPersist` master has left the tree, so step 3 also asks `ssh -O check <destination>`
  for the master's pid and scans that process too. If no TCP peer turns up anywhere, sshunnel
  warns and carries on.
- **Upstream DNS servers** (resolved's, or `/etc/resolv.conf`'s without it). Routed into the device,
  their UDP would get ICMP administratively prohibited and DNS would stop working for the whole
  machine.

**Policy routing.** Routes go into the main table, and sshunnel adds no `ip rule` of its own: a rule
wouldn't vanish with the device. Another tool's higher-priority rule (Tailscale's table 52 with
subnet routes, say) can still win, so step 5 looks up each target's effective route. If one doesn't
land on `sshunnel0`, sshunnel warns and names the device that won. The connected-subnet refusal reads
link-scope routes from every table the rules consult, not only main.

## Privileged helper (T-007)
- The client listens on a unix socket in a private (0700) dir under `$XDG_RUNTIME_DIR` and runs
  `sudo -- <its own exe> helper --socket <path>`. sudo closes inherited fds and may put the child on
  a pty, so the socket carries both the requests and the TUN fd (SCM_RIGHTS), never stdin. The
  helper's stdin is `/dev/null`: given the terminal, sudo would put it into raw mode for the whole
  session, and a Ctrl-C would reach the helper alone.
- The client checks the helper's SO_PEERCRED uid is 0; the helper checks the client's uid is the
  user who invoked sudo (`SUDO_UID`).
- **The helper is the boundary, not the client.** With a `NOPASSWD` sudoers line, any process
  running as the user can start it, so it takes *targets*, never raw routes or domains. It
  re-parses them, re-runs every refusal against its own route snapshot, and works out the pinned
  routes' gateways itself. The client's checks exist to fail early, before ssh runs. The sudoers
  line therefore grants exactly what `sshunnel route` allows, and the README says so.
- What the helper does is a closed set: create `sshunnel0` (non-persistent, `IFF_TUN |
  IFF_NO_PI`), set its MTU, add `198.18.0.1/15` and a ULA address (so v6 targets have a source on a
  v4-only network), add routes to the device, add pinned host routes via the pre-TUN route, and set
  the link's resolved config: DNS `198.18.0.2`, one `~suffix` routing domain per pattern,
  `DefaultRoute=no`, DNSSEC and DNS-over-TLS off for that link (fake answers are unsigned).
- Pinned routes carry a distinctive `proto` number. The helper deletes them on exit, and every
  start deletes leftovers carrying that number, which covers a SIGKILL of the helper. The README
  gives the manual equivalent (`ip route flush proto 222`, v4 and v6).
- The helper treats SIGINT, SIGTERM and SIGHUP like its socket closing: a Ctrl-C in the terminal
  reaches it through sudo too, and it must still delete its pins. The client treats the helper
  dying like the session dropping, and exits.
- `sshunnel0` already existing and in use is the "one session at a time" error (uat-011).
- Already root (euid 0, as inside a test namespace): run the helper without sudo.
- At teardown the helper closes the client's socket (so a client still running hears it is
  stopping before the device goes), then deletes its pins and then the device, while its own fd
  still holds it, and the device's addresses, routes and resolved link config go with it. It doesn't leave the device to
  the last fd: any fd's holder can set the persist flag without a capability, so a client could
  otherwise keep the device past the helper. An error or a panic after setup undoes the same. The
  device still goes with the last fd when the helper dies without its teardown, so a SIGKILL leaves
  nothing but pinned routes behind.

## Netstack (T-005)
- smoltcp drives an `Interface` over a packet-device trait: the TUN fd in production, an in-memory
  pipe in tests. It owns `198.18.0.2` and runs with any-IP, so it terminates connections to every
  routed address.
- Packets are classified before smoltcp sees them:
  - **TCP SYN** with no socket yet: check the policy (a CIDR target minus excludes, or a fake
    address whose name the current session's patterns match). Not allowed: RST. Allowed: hold the
    SYN, call `tunnel.open(host, port)`, drop retransmitted SYNs meanwhile. On success, create a
    listening socket for that endpoint and replay the held SYN, so the app gets its SYN-ACK at once.
    On `OpenErr`: refused is an RST, unreachable is ICMP host unreachable, timed out is silence
    (the app's own timeout fires).
  - **UDP to 198.18.0.2:53:** the DNS server.
  - **Other UDP and ICMP:** ICMP administratively prohibited (v4 type 3 code 13, v6 type 1 code 1).
- An established smoltcp socket becomes a `Stream` peer through an `AsyncRead + AsyncWrite`
  adapter, so M1's `pump` carries it unchanged.
- Fake addresses resolve to `Open{host: name}`, CIDR addresses to `Open{host: "10.99.0.5"}`. The
  relay dials either.
- Builder's call: how the interface loop and the adapters share sockets and wakers, buffer sizes,
  the device MTU (large is likely faster), and a cap on held SYNs. They decide uat-012.

## Names (T-004, T-006)
- The DNS server sees only queries under the patterns' suffixes, because resolved routes nothing
  else to the link.
- Per query:
  - Excluded, or not matched (for example `a.host.corp.example` under the exact target
    `host.corp.example`): forward the raw packet to the normal upstream servers and relay the
    answer. Upstreams come from `/run/systemd/resolve/resolv.conf`, read before the link is
    configured, minus `198.18.0.2`. Forwarding is UDP only, taking any answer UDP carries (up to
    64 KiB); an answer the upstream truncates (TC) fails, since the stack answers TCP to
    `198.18.0.2:53` with an RST, and the README says so.
  - Matched: `tunnel.resolve(name)`, cached 60 s positive and negative. NXDOMAIN on the remote is
    NXDOMAIN; any other failure is SERVFAIL. If the name exists: an A query gets its fake address,
    and every other type gets NODATA.
  - Answers carry a 5 s TTL, so a stale fake address fades quickly after an exit; negative answers
    carry a synthetic SOA with the same minimum.
- Fake addresses come from `198.18.0.0/15`. `198.18.0.0/24` is reserved (`.1` is the device, `.2`
  the DNS server), leaving about 130,800 slots. A name, lowercased and without its trailing dot,
  hashes (sha256, already a dependency) to a slot, probing linearly past a taken one.
- The map persists in `$XDG_STATE_HOME/sshunnel/names` (default `~/.local/state/sshunnel/names`),
  one `address name last-used-day` line per entry, rewritten by rename. A persisted entry wins over
  the hash. Entries unused for 30 days are pruned. The map is global, not per destination: a name's
  address is the same in every session, and a fake address whose name the current session doesn't
  match gets an RST.
- The relay's `Resolve` uses `getaddrinfo`, through the `libc` crate (bindings only, no C) so it can
  tell `EAI_NONAME` from other failures.

## Protocol v3 (T-002)
- `Resolve{stream, host}` on a fresh client stream id, answered by `Resolved{stream}` or
  `ResolveErr{stream, kind}` (no such name, other failure), so it reuses the stream table's
  correlation and teardown.
- `OpenErr` gains a `kind` byte (refused, unreachable, timed out, other) ahead of its reason.
- `VERSION` goes to 3; an older relay is refused by version (T-025's check) and the new hash pushes
  the new relay.

## Transport boundary (T-001)
A `Tunnel` trait in the client library, `open(host, port) -> Stream` and `resolve(host)`,
implemented by the mux session. `forward` and `route` depend on the trait, not on `Mux`. A later
QUIC backend (PRD-0003) implements it with native streams.

## Tests (T-010)
- **No privileges (`cargo make ci` everywhere):** target parsing and policy; refusals over a
  synthetic route table; the fake-address map (stability, collisions, persistence, pruning); the
  DNS server against a fake tunnel and a local stub upstream; the netstack against a second smoltcp
  interface playing the app (held SYN, RST, ICMP, data integrity through an in-process relay);
  protocol v3 frames; the relay's `Resolve` on `localhost` and `nonexistent.invalid`.
- **Network namespaces:** the test binary re-execs itself as root over fresh user, mount, PID and
  network namespaces. The fake remote runs in a second network namespace, with targets on a dummy
  interface there, so routed traffic can't loop back into the device. These cover the real TUN
  device, routes, refusals against real routes (a connected subnet, a destination already routed),
  teardown on every exit path, pinning (ssh's peer, directly or behind a `ProxyCommand`, a
  control master, an upstream DNS server, and none for a peer with a host route), one session
  at a time, and what the kernel tells the app when the remote refuses a connect or can't route
  it (ECONNREFUSED, EHOSTUNREACH). Patterns are refused there, since resolved serves only the host's namespace; the DNS
  server itself is tested at integration level, against a fake tunnel.
- **Where Ubuntu restricts user namespaces** (its AppArmor hardening, 23.10 on), each namespace
  test runs in a privileged container built from the host's own Ubuntu release plus iproute2 (and an
  ssh client, for the bench), so host-built binaries run unchanged and nobody changes a sysctl to
  run `cargo make ci`.
- **resolved, on the host, CI only:** `e2e_resolved_*` run under sudo on the ephemeral runner,
  through `getent`, then check the link config is gone (the route-root step). Locally they skip.
- **sudo, on the host, CI only:** `tests/route_sudo.rs` runs `route` as a user does: as the runner's
  own user, through the real sudo, on a pseudo-terminal whose foreground job it is, routing a
  pattern. A Ctrl-C typed there must end the run with exit 0, nothing left and the resolved link
  gone. CI's route-sudo step runs it next to route-root, both without retries. Locally it skips.
- Where namespaces or root aren't available, tests skip with a warning, and fail when `CI` is set
  (the convention the login-shell tests already use).
- CI adds a step, `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, before
  `cargo make ci`, and a step forcing the container path so it can't rot.

## Bench (T-011)
`cargo xtask bench --route` measures route against forward, single stream, each direction, through
a throwaway sshd on the host. Both modes' client side runs as root in a network namespace of its
own: through `unshare` where user namespaces work, else as root in the tests' privileged container
(the same detection and image). It reaches sshd through a unix socket, since a path crosses network
namespaces: ssh's `ProxyCommand` is `cargo xtask bridge <socket>`, and the bench process carries the
socket to sshd's loopback port. A sink and a source listen on every host address. Route mode's
target is the host's own first non-loopback IPv4 address as a `/32`, which the relay, on the host,
dials locally; forward mode's `-L` dials the same address through the same bridge, so both pay the
same overhead. Rounds interleave the modes, alternating which goes first, 15 of them unless
`--runs` says otherwise. The bench prints each mode's median and best and route / forward, marking a
median ratio below 0.90, and exits non-zero, naming each direction whose median misses. Below 90%
stops the milestone for a decision.

# Assumptions
- The client is Linux with `/dev/net/tun`, iproute2 and sudo; domain patterns also need
  systemd-resolved (v256 or newer behaves as described; older versions are untested).
- Apps use the system resolver. Browsers using DNS over HTTPS bypass the patterns (CIDR targets
  still catch their traffic).
- No other tool's policy routing outranks the main table for the targets. Where one does,
  sshunnel warns rather than fights it.
- smoltcp on a large-MTU TUN can stay within 10% of forward mode. This is the milestone's main
  risk, which is why the bench has a bar.
- The remote is as PRD-0002 assumes. Its `getaddrinfo` is musl's, so names resolve from the remote's
  `/etc/hosts` and `/etc/resolv.conf` only (no mDNS).

# Constraints
- No contributor machine change: where `kernel.apparmor_restrict_unprivileged_userns` blocks user
  namespaces, the tests use Docker. Lifting it stays an option the README's contributor notes
  describe, with what it trades.
- The relay may add the `libc` crate (bindings, no C) and nothing heavier.
- Public repo: documentation names and ranges only (corp.example, 10.99.0.0/16, 192.0.2.0/24); no
  personal hostnames, suffixes or addresses.
- No crates.io publish or release tag until Aaron confirms directly.
- Docs move with the code: a task that changes what a user runs, sees or installs updates the
  README, the CHANGELOG and (for new modules or commands) CLAUDE.md in the same commit.

# Non-Goals (MVP)
- macOS, full tunnel (`/0`) and keeping ssh's own traffic out of one.
- UDP, ICMP and raw DNS forwarding (SRV, TXT, MX); fake IPv6 addresses.
- Search domains (bare names), side-by-side sessions, reconnecting, config files or profiles, and
  a daemon mode.
- Resolvers other than systemd-resolved.
