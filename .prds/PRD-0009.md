# Summary

0.2.2 shipped with a list of findings its reviews judged fine to ship and parked in
`PRD-0008.log.md`. This PRD fixes every one of them and ships them as 0.2.3. It also adds the
follow-up one of PRD-0008's rulings named: `sshunnel sudoers` writes its `NOPASSWD` line for the
user's uid, so no login name is refused.

# Problem

Each item is small, but together they are the rough edges a careful user, an agent, or the next
contributor hits:

- **`sudoers` refuses some users.** A login sudoers would read as someone else (`ALL`, a leading
  `+`, an all-caps name, which reads as an alias) gets a refusal and has to write the line by hand.
- **The probe guesses.** Any exit before the root helper connects counts as "sudo prompts",
  including a helper that sudo started and that then failed. Both exit 1, so `--check` says "asks
  for a password" for what is really a broken helper.
- **Signals.** A Ctrl-C while `sudoers` asks sudo can leave an empty socket dir in
  `$XDG_RUNTIME_DIR`. `--check`'s help says it exits 0 "otherwise", but a signal makes it exit 1.
- **The check's output.** A binary replaced while it runs (`/proc/self/exe` reads `... (deleted)`)
  makes the `sudo` line `fail` with a confusing error. A multi-line detail, such as preflight's
  joined refusals, puts its continuation lines at column 0, under the check names.
- **Help that's wrong somewhere.** On macOS, the guide's last line points at `route` and
  `sudoers`, which don't exist there. A `route` refusal and a doc comment say "nss-resolve" where
  the check looks for `resolve` on the `hosts:` line.
- **Code that can drift.** `probe_with` repeats `start_with`'s socket-dir, bind and spawn steps.
  `completable()` restates the CLI's name and version, so a root argument added to `Cli` later
  silently drops out of completions. The non-unix `StopSignal` registers lazily, and no target
  CI checks compiles it. Nothing pins that `forward` registers its signals before its ready line.
- **Tests that pass or fail for the wrong reason.** The Troubleshooting test accepts a quote found
  in test code or a comment. The completions test fails if a description ever says "helper", and
  covers three of the five shells. One `sudoers` test fails on NixOS, and the e2e `sudoers` test
  fails from a checkout path with a space in it.
- **Docs warnings.** `cargo doc` prints five private-link warnings, and nothing in the gate notices.

# Goals

1. `sshunnel sudoers` works for every user, with a line visudo accepts.
2. `--check` and `sudoers` never report a failure as a prompt, and never leave files behind on a
   signal.
3. The help is true on each platform it ships for, and its tests check product code only.
4. The code that could drift reads from one source: one helper launch, one CLI definition.
5. `cargo make ci` fails on a new rustdoc warning.
6. Ship it all as 0.2.3, with no public signature changed.

# Technical Approach

**The `#uid` line (T-001).** sudoers accepts `#uid` wherever it takes a user name. sudo has for
decades, and sudo-rs 0.2.13's `visudo -c` accepts `#1000 ALL=(root) NOPASSWD: ...` (checked on this
machine). The file the script installs gets two lines, the name as a comment, then the rule:

```
f=$(mktemp) &&
  printf '%s\n' '# me' '#1000 ALL=(root) NOPASSWD: /usr/local/bin/sshunnel helper --socket *' > "$f" &&
  sudo visudo -cf "$f" && sudo install -o root -g root -m 0440 "$f" /etc/sudoers.d/sshunnel
```

`sudoers::script(user, exe, exe_root_only, sudo)` keeps its signature (principle 1). It takes the
uid from the process with `getuid()`, since the script is already for whoever runs it: it refuses
`AlreadyRoot`, and its answers come from this process's probe. `user` becomes the label only:
- The comment line appears when `user` is non-empty and plain (`[A-Za-z0-9._/+-]`).
- Otherwise the file has the rule alone, and nothing is refused for the name.

`misread_as` and its refusal go. `run()` passes `user_name()`'s name, or `""` when `id -un` fails,
so a uid with no name (a container, say) still gets its line. `user_name()` stays public and
unchanged.

**The probe tells a failed helper from a prompt (T-002).**
- sudo exits 1 when it won't run a command without a password (sudo-rs 0.2.13 does too, checked
  here). A helper that fails exits 1 today too, through `main`'s error path.
- So the helper gets an exit status of its own. `route::helper::FAILED` (`3`) is a new public
  constant, and `main` maps every error from `Command::Helper` to it. Status 2 stays clap's usage
  error.
- `probe_with` reads the status sudo exits with before the helper connects:
  - 1 is `Sudo::Prompts`.
  - `FAILED` is an error: "the root helper failed before it connected".
  - Anything else is an error naming the status: "sudo exited with N".
- `handshake`'s early-exit message tells `FAILED` apart the same way, and gives the sudoers hint
  only for 1.
- Exit statuses through `-n` are what sudo documents. A signal-killed helper shows as a status
  other than 1, so it falls into "sudo exited with N" rather than "prompts".

`probe_with` and `start_with` share a private `launch(base, command_line)`. It creates the
`SocketDir`, binds `helper.sock`, builds the command line and spawns `helper_process`, returning
the dir, listener, program and child. The probe still nulls the child's stderr. Each caller keeps
its own wait.

**Signals in `sudoers` (T-003).** `sudoers::run` selects on `helper::Signals::respecting_nohup()`,
registered first, as `check::run_with` does. A signal drops the probe, and the `SocketDir` with it,
then fails with "stopped by a signal" (exit 1). The test mirrors
`route_check_stops_on_a_signal_and_removes_its_socket_dir`, with a sudo shim that hangs.

**A replaced binary (T-003).** On Linux, `current_exe()` of a binary replaced or removed while it
runs ends in ` (deleted)`. `sudoers` gets a private `own_exe() -> Res<PathBuf>` that fails with a
new public error type, `sudoers::Replaced`, displayed as "this sshunnel was replaced or removed
while it ran; run it again". Both `run()` and `ask_sudo()` use it. `check`'s `sudo_finding` turns
a `Replaced` error into `warn` with that text, since nothing about the setup is wrong, and
`sudoers` prints it as its error.

**Multi-line details (T-003).** `Finding`'s `Display` indents each continuation line of `detail`
to the column where the detail starts (`8 + 1 + status.len() + 2`), so a joined refusal reads as
one block under its check line.

**`--check`'s exit status (T-003).** `route.txt` says `--check` exits 1 if a check fails or a
signal stops it, and 0 otherwise. The README block follows through `UPDATE_README=1`.

**The CLI (T-004).**
- **Platforms.** The non-unix `StopSignal` goes. The workspace doesn't build for Windows at all:
  `std::os::unix` in the `sshunnel` library, and `libc`'s getaddrinfo and rlimit in the relay. The
  releases are Linux and macOS only. `src/lib.rs` gets `#[cfg(not(unix))] compile_error!(...)`
  with "sshunnel builds for Linux and macOS", so `cargo install` on Windows says so plainly.
- **Ready line.** `StopSignal` gets a `fn ready(&self)` that prints `ready_line` to stderr, and
  `forward` prints its ready line only through it. Holding a registered `StopSignal` is then the
  only way to print the line, which pins the order by construction rather than by a racy test.
  `session::ready_line` is unchanged.
- **Completions.** `completable()` starts from `Cli::command()`. It copies that command's name,
  version and root arguments into a fresh root with the visible subcommands, since clap can't
  remove a subcommand. A unit test in `bin.rs` compares the completion root's name, version and
  argument ids, and its subcommand names, against `Cli::command()`'s visible ones.
- **The completions test** covers all five shells. It asserts each shell's candidate syntax for
  the visible commands and the absence of that syntax for `helper`:

  | Shell | Candidate syntax |
  |---|---|
  | bash | `sshunnel,<name>)` |
  | elvish | `cand <name> ` |
  | fish | `-a "<name>"` |
  | PowerShell | `CompletionResult]::new('<name>'` |
  | zsh | `'<name>:` |

  A description that mentions "helper" can no longer fail it.
- **Guide.** Its last line names `forward` and `completions` for every platform, and `route` and
  `sudoers` "on Linux".
- **nss-resolve.** `lifecycle.rs`'s refusal and `resolver_wired`'s doc say what the check reads:
  `resolve` on the `hosts:` line of `/etc/nsswitch.conf`.
- **The Troubleshooting test** reads product code only:
  - it skips `src/help/` and `src/tests/`;
  - in each file, it reads only the lines before the first `#[cfg(test)]`;
  - it drops lines whose trimmed start is `//`.

**Hosts and docs (T-005).**
- **NixOS.** `sudoers_root_only_accepts_a_system_binary` skips, with a message, when
  `/usr/bin/env`'s canonical path is under `/nix/store` (group-writable, so it's correctly not
  root-only).
- **A path with a space.** The e2e refusal branch expects the install command only when the
  test binary's path is plain, and the commandless refusal otherwise.
- **Rustdoc warnings.** The five private-link warnings are fixed by naming the items in plain
  code spans:
  - `helper` → `decide_fake_v6` and `plan`;
  - `names` → `PRUNE_AFTER_DAYS`;
  - `without_ping` → `PING_ROOT`;
  - the relay's `nameservers` → `MAXNS`.
- **The gate.** A `doc-check` task runs `cargo doc --workspace --no-deps` with
  `RUSTDOCFLAGS=-D warnings`, and `ci` depends on it, so CI runs it too. CLAUDE.md's Commands
  section says so.

# Assumptions

- sudo and sudo-rs accept `#uid` as a sudoers user, and exit 1 under `-n` when they'd ask for a
  password. Both are checked on this machine (sudo-rs 0.2.13). CI's sudo is upstream sudo, which
  documents both.
- `visudo -cf FILE` checks a file's syntax as an unprivileged user (true for sudo-rs here). Where it
  doesn't, the visudo test skips after a known-good file fails the same way.
- `current_exe()` on Linux reads `/proc/self/exe`, which appends ` (deleted)` once the file is gone.

# Constraints

- No public signature changes. New public items allowed: `helper::FAILED` and `sudoers::Replaced`.
- `route::helper` stays the privilege boundary. The new exit status changes nothing it trusts.
- Clippy pedantic with warnings denied, and no new `allow`s.
- Edition 2024 makes `env::set_var` unsafe, so tests inject seams instead.
- Help text stays ASCII and hand-wrapped at 100 columns, and the README blocks are regenerated with
  `UPDATE_README=1`.

# Non-Goals (MVP)

- Windows support. The non-unix branch goes, and a clear compile error replaces it.
- A `sudoers` that installs anything itself: it still prints a script for a person to read.
- Changing `-k` in the probe: a fresh sudo timestamp still reads as "asks for a password", per
  PRD-0008's ruling.
