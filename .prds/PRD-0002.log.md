# PRD-0002 log

Long-form notes that outgrew a task's `notes` field.

## T-012 -- 2026-10-15

`cargo xtask bench`: 512 MiB per transfer (256 MiB for the sweeps), best of 3, through a
throwaway non-root sshd on loopback (OpenSSH 10.2p1, x86_64 Linux). Both clients use the same
sshd, keys and `-F /dev/null`; sshunnel runs the release client with the embedded musl relay
(`opt-level = "z"`).

### Window sweep (the per-stream credit, `Config::default`)

| window | upload | download | download x8 | vs `ssh -L` (single stream) |
|---|---|---|---|---|
| 256 KiB | 346 MiB/s | 269 MiB/s | 476 MiB/s | 52-69% |
| 512 KiB | 417 MiB/s | 405-435 MiB/s | 488-503 MiB/s | 80-83% |
| 1 MiB | 484 MiB/s | 449-490 MiB/s | 490-499 MiB/s | 84-99% |
| `ssh -L` | 492-516 MiB/s | 485-533 MiB/s | 541-562 MiB/s | |

Single-stream throughput tracks window ÷ round trip, and the round trip crosses the relay, sshd,
ssh and the client, each a scheduler wakeup. Parallel streams were fine at every size (each has its
own window), which is what pointed at the window rather than raw pipe speed. 1 MiB is the default:
it lands within a few percent of `ssh -L` here, sits under OpenSSH's own 2 MiB channel window, and
keeps one stream unthrottled on a ~100 ms mobile link up to ~80 Mbit/s. Memory stays bounded at
window × streams.

### Rejected: relay stdio as non-blocking pipes

At 256 KiB, replacing tokio's blocking-pool `stdin()`/`stdout()` with
`tokio::net::unix::pipe::{Receiver, Sender}::from_owned_fd` moved single-stream numbers within
noise (366-377 up, 282-332 down) and cut 8-stream download from 476 to ~385 MiB/s: on the
current-thread runtime, the blocking pool was quietly giving the relay a second thread for its stdio
syscalls. Not worth the extra code; revisit only with a profile in hand.

### Bootstrap

Time from spawning `sshunnel forward` to both forwards ready: 145 ms pushing the 605 KB relay,
111-122 ms from cache. ssh's own connection setup is most of it.

### Follow-ups worth having

- Window auto-tuning (grow a stream's window while it is credit-bound, up to a cap): a single
  stream on a high bandwidth-delay link (1 Gbit/s × 50 ms) is capped near 20 MB/s at 1 MiB.
- Measure over a real WAN link, not just loopback.

## M1 review -- 2026-10-16

A code review of 6b8fc22..17e103a. Verdict: ready with fixes. The mux design held up (flow control
as planned, race-free teardown, a reader that never blocks); the findings below became T-015..T-024.

- **Critical (T-015).** The bootstrap's cache-hit loop never ran the ownership and symlink check
  that the staging and install loops ran, which broke this PRD's own rule for the shared-tmpfs dirs.
  With no `sha256sum` on the remote, a cached relay was checked by size alone, and `safe()` tested
  for a symlink before calls that follow one. Fix: one trusted-dir predicate built on a single
  `ls -ldn` (lstat) owner test, applied to all three loops; `chmod` only after it passes; a cached
  relay must be a regular file the user owns; and a cache hit requires a real sha256 (`sha256sum`,
  `shasum -a 256` or `openssl dgst -sha256`), so a remote with no hasher always receives the relay.
- **Important.**
  - T-016: `Frame::decode` froze payloads out of the reader's buffer, so each small queued `Data`
    payload kept a whole ~64 KiB block alive. Measured: 292 KiB of queued payload grew the heap by
    188 MiB, about 650 MB per stalled stream at the 1 MiB window. Goal 3 did not hold.
  - T-017: `Mux::open` allocated the id under the table lock but queued `Open` after releasing it,
    so concurrent opens could reach the relay out of order, and the relay resets any id at or below
    the last it saw. 8 threads × 20,000 opens: 127-135 spurious failures; 0 with the send inside
    the lock.
  - T-018: one `accept()` error (EMFILE: macOS defaults to 256 descriptors) returned from `serve`
    and ended the process.
  - T-019: `e2e_a_cached_relay_with_the_wrong_bytes_is_replaced` called `set_mode` on a copy of the
    permissions, so the planted file stayed 0644; flipping an ELF byte would also have failed
    `--probe`. The sha256 re-check on cache hits had no test.
- **Minor.** The memfd fallback leaked its staged file when python failed before `unlink`, and
  `vm.memfd_noexec=1` also defeats it under flags 0; ENOSPC or a quota in the first writable dir
  reported "corrupted" without trying the next; `sha256sum "$1"` escapes odd names (use stdin);
  `--probe` inherited the session as stdin; old relays were never removed; `$$` staging names can
  collide on a shared NFS home (T-020). A stream the peer had half-closed lingered after a reset
  when its local side was idle (T-021). The window was protocol but never on the wire (T-022). The
  default bind was IPv4-only where `ssh -L` binds `localhost` (T-023). Missing tests: an
  over-credit `Window`, dropped `Open` and `Pending` streams, teardown mid-open; the `write_loop`
  comment claimed control frames always precede later data, which two channels can't promise
  (T-024).
- **Declined:** window auto-tuning (already a follow-up), terminal escapes in the remote's READY
  line, a hostile relay flooding `Open`s, timeouts that ssh already owns, Ctrl-C semantics,
  reconnects (a non-goal), and the bench's loopback-only method.

## Fix review -- 2026-10-17

A review of the T-015..T-024 commits (ffb9c54..1867853), read-only, with the script exercised under
dash, bash and busybox ash against GNU, uutils and busybox tools. Verdict: no correctness bugs; each
commit fixes its finding.

- **Taken (T-025).** An e2e test for the owner comparison itself (an `id` shim reporting another
  uid) and one that runs the whole bootstrap under busybox alone (`busybox --install -s` as
  `PATH`). A hit no longer runs `chmod` (it needs the dir private already), so a read-only cache
  keeps its hits. A hasher that gets the sha256 of empty input wrong is dropped, so such a box pushes
  every run instead of failing with "corrupted". `Hello` decodes its version before its layout and
  `VERSION` is 2, so an older relay is refused by version. Plus: the error names ownership, a family
  the host lacks no longer warns on every run, `Mux::open` registers before queuing `Open` as the
  `write_loop` comment says, the `Config` doc, and `ls` in the README's requirements.
- **Declined.** A parent-dir check on each candidate: the parents are the user's own or sticky system
  tmp dirs, and the check costs a process every run. Clamping a peer's window for 32-bit targets:
  there are none.
- **Throughput.** Interleaved A/B, 256 MiB best of 3, on a box with load swinging 2-21. The first
  T-021 (a `Notify` raced on every upload read) cost ~4% of download: 447-457 against 463-476
  MiB/s. Arming it only after the download is done (dd1ed27) put download level with the baseline.
  Download x8 sat ~4% lower in every variant after T-020, including one with no `select!` at all,
  so it isn't pinned on a change at this noise level.
- **Bootstrap.** The fixes added processes per run (`ls`, `chmod`, `touch`, eviction subshells):
  push 144 -> 188 ms, cached 109 -> 130 ms against the pre-fix script, five interleaved rounds.
  A builtin `[ -f ]` prefilter, no `chmod` or `touch` on a hit, one `find` for eviction (by install
  age), and no re-check of the staging dir brought it to 138 / 119 ms; the rest is the two `ls`
  owner checks.
